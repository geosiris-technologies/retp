# Conformance suite (`retp-conformance`) - architecture

Related decision: [ADR 0005](../../docs/adr/0005-conformance.md) (conformance is judged apart from the client: one check, one cited rule, one verdict).

## Purpose and position

Judging an ETP v1.2 server against what the specification makes mandatory, and writing the report a provider can act on. It is built on the client (`retp-client`) and the protocol core, and **nothing else in the repository depends on it**: what a server is judged on must never leak into what the client tolerates.

## Rules

- **One check, one cited rule, one verdict.** `Finding { id, section, rule, protocol, verdict, said }`: the specification section, the rule in its own words, and *what was seen*. A provider reads the table of failures; without the cited rule and the observation there is nothing to fix.
- **Five verdicts, and the difference is the report**: `Pass`; `Fail`; `Tolerated` (a fault the client took as meant, the negotiation's `deviations`); `NotApplicable` (the server does not announce the protocol; §3.1.1.2 ¶3 makes a protocol mandatory only when announced); `NotChecked` (no check, or nothing to observe). **A check that could not observe answers `NotChecked`, never `Pass`**: a green report for an unreachable server would be the worst possible result.
- **Every request goes through `ask`**, which keeps the received headers (`Seen`): the wire rules (odd and increasing identifiers, correlation, FIN) are verified on **everything** the pass received, not on a request chosen to pass.
- **The order is that of a client**: session, dataspaces, content of a dataspace, one object; each step hands the next what it found, and the next says `NotChecked` when there is nothing.
- **Writes happen only with `--write`**, in a dataspace named after the suite, created and then deleted whatever happens between. The server under test belongs to its operator. A name already listed is never written. **Only what the suite wrote is deleted** (`delete_ours`: an object it put, in its dataspace, with the sample prefix); a dataspace is deleted only if it holds nothing else. If creation is refused, samples go into an **existing** named dataspace and only what the suite put there is removed. **Whatever the store adds on its own stops every deletion**: the suite lists the dataspace before writing, anything appearing without being its own (`store_made`) makes it keep everything it wrote, and the report says why, by type.
- **Samples** (`samples.rs`) are fourteen objects of six families (EML 2.0/2.3, RESQML 2.0.1/2.2, WITSML 2.1, PRODML 2.3), closed and re-read strictly by the library (`the_samples_are_valid_documents`): a server refusal is a finding, never a defect of our XML. Arrays written are a small set of triples copied into the code (never read from a file), with doubles that a 32-bit float cannot hold and enough rows for a sub-array to be a real part. An array hangs off **the object that references it**, never off the proxy (the specification admits both, §23.32.3). One is written whole, the other declared then filled in two blocks; each gets metadata and a middle-rows sub-array read. **One defect, one failure**: the round trip (`write.array.read-back`) fails saying the doubles came back rounded, and the blocks and sub-array that landed where sent do not fail a second time. Each rule has a knob on the fake store (`shifted_subarrays`, `forgets_block_keys`, `transposed_metadata`, `stores_float32`).
- **The fake store has knobs** (`tests/self_check.rs`): one per rule a store can break without the session refusing, and each test turns one and reads the verdict that must go red. **Adding a check means adding the knob that turns it red**, or it may be looking at nothing.
- **`checks::run` is written over the `Session` trait**, which both the WebSocket client and the REST remote implement, so the same pass runs on both. What REST lacks (session, `Acknowledge`, wire headers, raw faults) answers `NotApplicable` saying so, never `Pass`: over REST the headers are the client's bookkeeping and judging them would be judging this crate. "Connected" over REST means the dataspaces answer, since a health route answers on many APIs.
- **Raw faults** (a client never sends them) go through `raw.rs`: a second session driven by hand over a bare `Transport`; a forged message takes the identifier of a `Ping` the wire just emitted so numbering stays correct. Protocols not negotiated get one request each of reads and creations (never deletions), `EUNSUPPORTED_PROTOCOL` expected.
- **Every protocol granted has its reads tested**, on the server's own data (`reads.rs`): tombstones, an object's neighbours, several objects at once, JSON, a channel's metadata and ranges, a notification subscription. They are sent by `ask`, not through the client, which swallows a refusal.
- **With no dataspace listed or protocol 24 absent, read `eml:///`**, which every store MUST serve (§21.2.2 row 1). Object URIs are built by `EtpUri::object` (a string format gives `eml:////…`), and `is_ours` compares parsed dataspaces, not a prefix.
- **A timed-out request reopens the session** (`renewing::Renewing`): the check that sent it fails and the next runs on a fresh session, the note saying so. The suite announces a `ResponseTimeoutPeriod` of 60 s (`with_patience`), the capability of the side that waits (§3.3.2.3).
- **The report is written as the pass runs**, so a run stopped from outside leaves what it had seen. It starts with the connection notes, what is supported (read from findings, never `yes` for something not observed), the requests with their times, and the objects written. A null `activeStatusFilter` that a store cannot read is re-asked as `active` then `inactive`, and `discovery.null-filter` says how the null was taken. The exchange annex (`exchanges.rs`) records every request and response, headers included, in the ETP JSON encoding, so a provider can be told exactly which URI was sent.
- **Pre-session checks** (`.well-known`, the verified TLS chain) need the native network and have no fake; `--tls-fallback` verifies, records a failure and a note when refused, and runs the rest unverified. The connection is `login::Choice`'s (token, Basic, client credentials, password grant), a refusal of the token service being `login.token`, not a server failure.
- **The report header says** it is produced by a tool and that a failure may be the tool's.

## Tests

`tests/self_check.rs` is the whole safety net: every check has a knob that turns it red, and every deletion rule has a sabotaged test (existing dataspace, a foreign object, the fallback, the next dataspace, objects the store made). Run with the workspace: `cargo test --workspace --test self_check`; usage: `etp-conformance wss://host/etp --user X` (secrets from the environment), `--write`, `--out report.md`.
