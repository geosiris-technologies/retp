# Client (`retp-client`) - architecture

Related decisions: [ADR 0001](../../docs/adr/0001-client-architecture.md), [ADR 0002](../../docs/adr/0002-decisions-by-tier.md), [ADR 0003](../../docs/adr/0003-session-and-resumption.md) (resumption, idempotent replay).

## Purpose and position

What a client does with the protocol: it puts a transport, a clock and the operations a client asks for on top of `retp-proto`. The `retp` command (`retp-cli`) is argument parsing over this crate. Networking is native-only; the rest compiles to WebAssembly (checked in CI).

## Rules

- **Two clients on one engine.** `engine::Engine` is the client without transport or clock: bytes in, an outbox, responses filed **per request** (several can be in flight; an answer goes to its own request, never to the first one waiting). The blocking `Client` waits on a `Transport`; the `AsyncClient` is fed by whoever owns the socket (`received`, `tick`, `lost`) and answers with futures, which is what a browser worker needs. All request logic is in the engine; neither client holds any.
- **Each operation is written once**, as an `async fn` over the `Caller` trait; the same-named functions at the crate root run it on the blocking client. Writing an operation twice, blocking and async, is what this crate refuses.
- **Several requests in flight go through `Caller::call_all`**, which returns one result per request in the requested order whatever the order of answers, keeping `at_once()` in flight (4 by default). Plural operations use it, not `call` in a loop; a failing group loses only itself.
- **A stream is read apart from the unexpected.** Unsolicited messages are routed by the protocol of their header: subscribed, they go to that protocol's queue, otherwise to `unsolicited`. Unsubscribing hands back what was kept. This is the primitive of notifications, channel subscribe and channel streaming.
- **The transport is a trait and the tests have a fake** (`memory::MemoryTransport`, public so the bridge crate can use it): the other end is an in-memory server `Connection` and the clock advances exactly by the time asked to wait, so a five-minute timeout is tested in an instant on the very client the CLI uses. A test that can hang never fails: past an hour of test time the transport drops the connection.
- **The network lives in `native.rs`; nothing of it compiles for wasm** (`cfg(not(target_arch = "wasm32"))`, down to the `Cargo.toml`). **rustls uses `ring`, never its default `aws-lc-rs`**, which needs cmake and nasm to build; a `rustls` added elsewhere with default features would pull `aws-lc-rs` into every build.
- **A server profile touches only the handshake** (`ServerProfile::adapt(Handshake)`); `Client::open` takes no profile. A divergence that must go further goes through it.
- **Obtaining a token is `login.rs`'s business** (§4.1.2): one `Login` per way in (token, Basic, OAuth client credentials, password grant, Cognito-style); what can be verified without a network (`client_secret_basic`, `SECRET_HASH`, response parsing) is a pure function held against RFC examples. **`Login` does not derive `Debug`**: it carries secrets. The choice of connection is `login::Choice`, nowhere else: faces pour their options into it, it reads secrets from the environment through a given function (testable), and decides (a token URL with a user is the password grant, RFC 6749 §4.3; without, client credentials). An `invalid_client` answer to `client_secret_basic` is retried **once** with `client_secret_post`. Token services are always reached over verified TLS: `--insecure` concerns only the ETP server and is reported each time.
- **A request that never reached the socket is reported as not sent** (`Interrupted { sent: false }`); **an interrupted write is neither success nor failure** (`Interrupted { sent, confirmed }`): the store may have committed and lost the answer. It is reported and a person decides; it is never replayed alone. The shell replays only what is idempotent: a cut read restarts on a fresh session, and the shell prints the argument `changes-since` expects so the caller can catch up.
- **Resuming is an order, and the fallback is the real path.** `reconnect` first tries a server resumption (`Connector::resume`, `None` by default), then opens a whole session, and **says** why the resumption did not serve. What actually recovers data is the watermark catch-up: the runner keeps the `Continuity` across steps (once the socket is dead the watermark can no longer be read) and tells the operation since when to ask again, or that it is too late.
- **Long operations run through the runner of `resume.rs`**: a `Connector` and an `Operation` that advances by steps. A retryable failure (connection dropped, timeout, refused answer) opens a new session after a doubling pause; `max_retries` counts **consecutive** failures of one step; a step that fails twice is halved. A server refusal on one object is not a step failure; it goes into the report. Downloads write under a temporary name and rename, so the files are their own journal across processes; a step removes from its queue only what it finished.
- **Streams and notifications have their own modules** (`notifications.rs`: store notifications, `changes_since` as the watermark catch-up; `channels.rs`: channel subscribe and streaming, typed `ChannelEvent`s). The client announces a protocol only if something handles it, and a consumer role for the streaming pair. `tell` sends a message that expects no response and is refused by name on a caller without a wire.
- **The REST client is one more `Caller`** (`rest.rs`): it receives the ETP request, calls the OSDU Reservoir DDMS REST API and returns ETP responses. A trait `Http` sends; the blocking client wraps it. Enumerations that the API gives as numbers are read through the **Avro decoder** (`by_ordinal`), never a hand-written table; what REST lacks is refused by name before any request. Its tests run the same operation through both transports against the same store. Only the official API is supported. Objects are sent as Energistics JSON only (XML refused by name); the three array writes go through one route, and a sub-array carries the dimensions of the whole array taken from the earlier declaration; a `PUT` answers a boolean, so `200 false` is a refusal.
- **An object the server holds without JSON is never said absent.** Plural reads are one request per dataspace; a JSON read can return `[]` for a whole batch if one object has no JSON. The client keeps the default, re-asks in XML for what is missing and halves the batch (`ENOT_FOUND` for the absent, `ENOSUPPORTEDFORMATS` for the object without JSON).
- **A round trip costs more than its answer.** Requests of one ETP message go to the transport together (`Http::send_all`) and the transport runs `at_once` of them side by side. Grouping beats parallelising, and they add.
- **A REST enumeration is written as an ordinal *or* a symbol, and both are read**, through the generated tables. An absent `transportArrayType` is implied by the logical type (`rest::implied_transport`), never invented; base64 is not `bytes` (it is the value encoding of any numeric transport).
- **A request is checked against the specification before it is sent**, and a violation is a `ClientError::Invalid` (non-canonical URI, a `scope` that `GetSupportedTypes` does not admit, a format the session did not retain); the session stays open.
- **The client takes everything it is sent.** The retained types are the server's answer, **never a filter**: an object of any type is read. Without `--type` the offer widens to the types the server's probe announces; a refused probe leaves the offer as is.
- **A server says no with `successful: false`, not an exception** (the three Transaction responses). `Opened` and `Ended` carry the refusal **and its reason**, and it is not a `ClientError`: `Invalid` means *not sent, session intact*. A refused commit is the costly one (the writes are not in the store); an interrupted commit is neither. An empty reason is reported as a refusal without a word. The returned transaction uuid is compared to the requested one.
- **A client that writes announces protocol 18** (`WRITING`), a separate list from `READING`: nothing is announced that nothing handles.
- **Arrays are read as §13.2.1.1 says** (`arrays.rs`): metadata first, then whole or in blocks according to **two budgets** and a pure `plan`. `arrays::budget` (message size minus a margin, and `MaxDataArraySize`) bounds one array or block; `arrays::message_budget` (message size only) says how many blocks travel together. Element size is the worst transport size for the message and the logical-type size for `MaxDataArraySize`. Every received block is checked (dimensions, value count, type) before being copied.
- **Writing an array is the same split as reading it**: `plan` decides the blocks both ways, so a writer and a reader cannot disagree. What fits goes in one `PutDataArrays`; what does not is **declared first** (`PutUninitializedDataArrays`) then filled block by block, the order the specification gives (§13.1.2). The walk over blocks is written once (`for_each_run`, used by both `Assembly::place` and `carve`): two walks of the same arithmetic is the bug shape this repository keeps finding. The test that catches it is a round trip, value by value.
- **Arrays of one island travel together, and it can be bypassed** (`Grouping::Together` by default packs whole arrays into as few messages as the negotiated budget allows and sends them with `call_all`; each array is answered **by its key**, so one refusal in five marks one array. `Grouping::OneByOne` sends one array per message). Automatic, and bypassable.
- **An array's identity is the pair (object URI, path in the resource)**, never the path alone, which is what `DataArrayIdentifier` carries. A server keyed on the path alone lets two objects sharing a path silently overwrite each other's arrays, and a redeclaration with other dimensions can corrupt it; a server must key on the pair and refuse an incompatible redeclaration.
- **A `null` in a JSON array is an absence, not a refusal.** JSON has neither `NaN` nor `Infinity` (RFC 8259); `null` is the only valid spelling, and the logical type says what it means. Refusing it lost the whole array, but a continuous property carries an absence per inactive cell. Arrays are read in **base64** wherever the API offers it: the IEEE bytes carry `NaN` for free.
- **Per-key answers keep their key** (`operations::keyed_answers`). A `ProtocolException` is either per key (this one failed) or single (the whole request failed); confusing them loses every key's reason at once. A key the store said nothing about is reported: an unreported write is not a write that worked.
- **Two ceilings bound a written object and do different things.** `MaxDataObjectSize` (§3.3.2.4), declared by the store, **refuses**: it will not hold the object however it is sent, so the request is refused before anything leaves, naming both numbers. What one **message** can carry **splits**: a larger object goes as `Chunk`s (§3.7.3.2): its `data` emptied, a `blobId` set, the bytes following in the same multipart request, the last chunk with FIN. Chunk size is `arrays::message_budget`; the `blobId` is the object's own uuid. A request in parts is `Caller::call_parts`, whose default refuses by name (REST has no BLOBs). The test is a byte-for-byte round trip.
- **`PutDataObjects` is an upsert** (§9.1.1): rewriting an object replaces it and is not a failure. Nothing reads before writing; that would double the round trips to enforce a rule the store does not have.
- **An acknowledgement can be asked for and is heard** (`ask_acknowledge`, flag `0x10`); an `Acknowledge` answers nothing, the response follows. **A waiting client listens** (`Client::idle`): between commands the transport answers WebSocket pings and the keepalive `Ping` goes out when due.
- **The interactive shell re-reads commands with the same argument definitions as the one-shot commands**, so an option added to one is added to both. A lost connection reopens a session and replays the command **once**, since the shell runs reads only.
- **Writes are never tried on a store that is not a test double or one's own.** Tests of the writing tier run against the in-memory `Store` of `tests/client.rs`.
- **The CLI holds no logic**: the offer, the requests and their refusals are here; the command reads arguments and prints.

## Tests

`tests/client.rs` (client over the fake transport and a real in-memory server `Connection`), `tests/etp_login.rs` (pure login functions against RFC examples). Sabotage was used to prove tests can fail (an inverted result order, a subscription not kept apart, a watermark not sent). Run through the workspace: `cargo test --workspace --test client --test etp_login`; `cargo check -p retp-client --target wasm32-unknown-unknown` verifies the wasm build.
